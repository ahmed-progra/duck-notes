# Security and privacy

Duck Notes is an offline Android notes app. The production app has no `INTERNET` permission, account login, analytics, or cloud-sync implementation. Local note text, derived search/link data, preferences, and images remain sensitive even when no server is involved.

## Storage and recovery limits

Duck Notes stores notes in Room/SQLite and images in its private app files directory. The app does not encrypt these files. Optional app lock requires the Android device screen-lock credential; it is a UI access control, not storage encryption. Unlock state stays in memory and is cleared on leaving, pausing, stopping, or losing the top resumed position of the Activity. Configuration recreation retains the session; process recreation does not. Screenshots and Recents previews are blocked with `FLAG_SECURE`. Loading or unreadable security settings do not expose note UI without device authentication; corruption recovery persists `lock_enabled=true`, so restarting cannot silently bypass the recovered lock. A device without a configured screen lock must configure one before a locked session can open. A person with an unlocked device, privileged access, a compromised operating system, or access to the user's backups may be able to read them. Trash is a reversible state, not secure erasure; archived and trashed content remains in storage and backup.

Unsupported database downgrades must fail without destructive fallback. Keep the current app and its data if a downgrade is rejected; clearing app data or uninstalling can destroy local notes. Save failures keep the originating editor's recoverable text and expose Retry. Recovery depends on the app process still retaining unsaved text; text that never reached persistent storage is not guaranteed to survive after a forced process kill or power loss.

New image imports accept PNG, JPEG, WebP, or GIF content after checking the actual image data. Each image is limited to 20 MiB of input; dimensions and decode sizes are bounded. Files are copied into a private temporary directory before publication. Publication uses a same-filesystem atomic move under the shared process lock and rejects an existing destination. The attachment row and note reference are committed in one database transaction. Image formats and their platform decoders remain a security boundary, so keep Android and dependencies updated.

Image removal records a durable cleanup intent before removing its row and note reference. Failed unlinks remain queued; main-process startup retries only recorded files whose attachment row is absent. These recovery records are included in backup. Persistent storage failures can postpone byte removal; deleting an image is not secure erasure.

## Portable encrypted backup and imports

Manual `.duckbackup` files use Google Tink Android's `AES256_GCM_HKDF_1MB` streaming AEAD. A random keyset is wrapped with AES-256-GCM using a key derived from the passphrase with PBKDF2-HMAC-SHA256, 600,000 iterations, and a fresh 16-byte salt. The format header is authenticated; the complete ciphertext must authenticate before archive parsing and restore. This protects the backup file, not the live database. Passphrases are not persisted and cannot be recovered.

Backups include note identities, text, timestamps, pin/archive/trash state, tag customization, and attachment bytes. They exclude credentials, device security settings, caches, and derived indexes. Restore adds missing note IDs in one database transaction, skips existing IDs, and keeps existing tag customization. Conflicting attachment identities or ownership are rejected. Recovery markers coordinate private attachment publication with startup cleanup. See [format and limits](docs/backup-format.md).

Markdown/plain-text imports always create new note identities. ZIP imports validate bounded metadata, UTF-8, entry names, duplicates, image bytes, and attachment ownership. Limits include 10,000 notes/images, 2 MiB per note, 64 MiB total note text, and 1 GiB archive/expanded data; additional metadata and tag limits are documented in [portability](docs/portability.md). Temporary staging is private and excluded from Android backup. Document-provider errors and cancellation are surfaced; an external provider can leave a partial file after a failed write. Sharing grants read access through a FileProvider restricted to prepared exports. Picker returns pass ordinary app authentication before note access or passphrase entry.

## Android backup

On Android 9 and later, explicit rules select `duck.db` and its SQLite sidecars, `attachments/`, and the settings/welcome DataStore files. Android 8 backup is disabled because that version cannot enforce encrypted transport requirements. Android 9-11 use separate include entries requiring either client-side encryption capability or device-to-device transfer; a combined flag value would require both. Android 12+ cloud rules set `disableIfNoEncryptionCapabilities=true`, and device-transfer rules remain separate. These are Android transport capability requirements, separate from the manual encrypted backup format. Import files under `attachments/.pending/` are excluded. Both legacy backup rules and Android 12+ cloud/device-transfer rules are present. Attachment references are portable app-owned keys; supported legacy paths are rebased into the restored app directory rather than opened at the old absolute location.

Android controls when backup runs, where the selected transport stores it, and how restoration is offered. These rules govern future backups; they do not erase copies created by earlier app versions. Google cloud Auto Backup has a **25 MB quota per app**; exceeding it stops that cloud backup until data falls below the quota. A 20 MiB image limit does not ensure an entire notes collection fits. Device-to-device transfer and OEM transports can behave differently. User backup settings and Android account/device protection also affect recovery and confidentiality. See [Android Auto Backup](https://developer.android.com/identity/data/autobackup).

## Repository and dependency checks

- `scripts/security_checks.py wrapper` verifies the pinned official Gradle 8.13 wrapper and distribution checksums and requires the dependency verification file before executing Gradle. Presence activates verification; Gradle checks the configured dependency bytes.
- Gitleaks 8.30.1 scans the source candidate and complete available Git history with 100% redaction. Reports and temporary source exports stay outside the commit.
- Gradle dependency verification must remain in strict mode. Checksum metadata constrains accepted bytes; generating metadata alone does not independently establish publisher authenticity.
- The resolved dependency inventory includes Android runtime, compile/test, buildscript, UTP, and observed task-time lint/AAPT dependencies. It records excluded raw metadata declarations and unused Native-only configurations by exact name and reason. Missing build coverage, resolution failures, and failed advisory queries fail the check.
- Guava JRE dependencies used by Gradle, annotation processing, and Android test tools are pinned to 33.7.2-jre, including the detached lint graph, to address [GHSA-xxph-c9ww-hj94](https://github.com/google/guava/security/advisories/GHSA-xxph-c9ww-hj94). The current app runtime does not include the full Guava library; future dependency changes still require a fresh resolved-graph advisory scan.
- Lint's detached tool graph has strict transitive constraints for patched Bouncy Castle, Commons Compress, and HttpClient versions. Its observed resolved graph must still pass the advisory scan; ordinary project configuration rules do not constrain that detached graph.
- Current OSV matches remain visible. The only nonblocking applicability disposition is `GHSA-r937-wjx7-w2jp` for `org.jetbrains.kotlin:kotlin-gradle-plugin:2.0.21`: the [upstream fix](https://github.com/JetBrains/kotlin/commit/bf51df665b458fda7c3eaf436c4d88dc119d7ec6) changes KAPT cache deserialization, while this build uses KSP. The disposition requires nonempty evaluated plugin/task/configuration evidence, no KAPT use or processor components, and positive KSP evidence. Introducing KAPT, changing the component version, or matching another advisory fails the check. This is an applicability decision, not a claim that the Kotlin version is patched.
- DataStore 1.1.2 includes relocated `protobuf-javalite` 4.28.2 through `datastore-preferences-external-protobuf`. This is patched for [CVE-2024-7254 / GHSA-735f-pc8j-v9w8](https://github.com/protocolbuffers/protobuf/security/advisories/GHSA-735f-pc8j-v9w8). Regression tests feed deeply nested unknown groups through the real private-file store and verify recovery with app lock enabled; shallow unknown fields preserve existing settings. The relocated copy remains outside standalone Maven-coordinate matching, so review its runtime version and current advisories whenever DataStore changes. A constraint on a separate protobuf dependency cannot replace relocated code.
- Maven matching does not cover every bundled native-library, Android-platform, JDK, or build-tool vulnerability. Bundled SQLite 3.46.0 has upstream version-range matches requiring attacker-controlled SQL/database metadata or concurrent WAL writers/checkpoints. Current production uses fixed bound SQL, a private database with no database import API, and Room's single writer. Those prerequisites were not found in this app; future raw SQL, database import, additional processes/builders, or checkpoints require a new assessment. See [SQLite advisories](https://sqlite.org/cves.html) and the [WAL-reset race](https://sqlite.org/wal.html#walreset). This conditional risk remains visible until a compatible patched official driver is qualified.
- CI has read-only repository permissions, immutable action commit pins, no persisted checkout credentials, and no signing or publishing step. Security finding reports are not uploaded as public workflow artifacts. Verification also runs weekly, dependency updates are proposed by Dependabot, and main requires a PR plus the GitHub Actions `verify` check. Updates still need review and device qualification.

Secret scanning is not proof that no secret or private artifact exists. Do not commit real notes, database copies, credentials, signing keys, provider grants, private evidence, or machine-local configuration. Use synthetic data in test fixtures and logs.

## Reporting a vulnerability

Report vulnerabilities through [GitHub private vulnerability reporting](https://github.com/ahmed-progra/duck-notes/security/advisories/new). Do not post real note text, credentials, or a working data-exposure payload in a public issue.

Provide the affected commit/version, Android version, minimal steps using synthetic data, expected and actual behavior, and the security impact. No response-time or supported-release commitment is currently published.
